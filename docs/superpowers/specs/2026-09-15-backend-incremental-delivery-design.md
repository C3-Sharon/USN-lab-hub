# 后端分块执行与透明交付设计

> 日期：2026-09-15  
> 状态：REVIEW  
> 适用范围：USN Lab Hub 每周 Java 后端工作  
> 目标：在不增加无效汇报和重复测试的前提下，使每周后端实现过程可观察、可暂停、可恢复、可验证。

## 1. 问题与目标

现有治理文档已经说明每周范围、角色职责、合并顺序和最终质量门，但后端从领取任务到提交 PR 之间缺少统一的过程载体。这会产生以下问题：

- 用户只能在最终结果出现后判断实现是否偏离契约。
- Agent 中断或更换上下文后，容易重新扫描仓库、重复推理和重复测试。
- 高风险数据库、权限、事务和并发决策可能在实现过程中被默认接受。
- 测试执行次数很多，但每次测试覆盖的风险类别不清楚。
- 最终 PR 内容过大，难以定位每个业务结果来自哪个工作块。

本设计要达到：

1. 每周后端工作开始前先拆成 3 至 6 个可独立验证的工作块。
2. 每块明确目标、输入、结果、验证方式和进入下一步的条件。
3. 普通工作块保持连续推进，高风险工作块必须由用户确认后继续。
4. 使用一个 Draft PR 持续展示过程，不增加额外周 PR。
5. 以仓库文档保存执行上下文，减少聊天重复和 Agent 恢复成本。
6. 测试覆盖新的风险类别后停止，不靠重复运行提高可信感。

## 2. 采用方案

采用“独立后端执行台账 + 单个 Draft PR + 混合阶段门”。

不把执行过程全部写入产品周文档。产品周文档继续回答“为什么做、做什么、契约是什么”；后端执行台账回答“如何实现、如何验证、当前做到哪里”。两者通过链接关联，不复制字段和状态枚举。

不把 GitHub Issues 或聊天记录作为唯一过程载体。GitHub 在可访问时用于展示提交和评审，仓库内台账才是 Agent 可恢复的事实源。

## 3. 文档职责

### 3.1 长期规则

| 文件 | 职责 | 计划修改 |
|---|---|---|
| `AGENTS.md` | 所有 Agent 不可绕过的最短规则 | 增加“后端先分块、按阶段门推进、更新执行台账”的入口规则 |
| `docs/governance/WEEKLY_DELIVERY_PLAYBOOK.md` | 团队每周协作、分支、PR 和联调制度 | 增加 Draft PR、工作块提交和混合阶段门流程 |
| `docs/governance/QUALITY_GATES.md` | 风险分级、测试层级和停止条件 | 增加工作块验证证据和高风险确认要求 |
| `docs/agent-guides/12_BACKEND_LONG_TERM_AGENT.md` | Java 后端 Agent 执行方法 | 增加逐块开工、汇报、暂停和恢复指令 |

长期规则只描述方法，不包含具体周次、接口或文件列表。

### 3.2 模板

新增：

```text
docs/backend/WEEKLY_EXECUTION_TEMPLATE.md
```

模板定义固定字段、状态和完成检查。修改流程规则时只修改模板，不回写历史周台账。

### 3.3 每周执行台账

每周在后端分支创建：

```text
docs/backend/execution/2026-WNN.md
```

文件名使用实际开发周编号，元数据同时记录路线第几周。每周只有一个后端执行台账。旧 `docs/backend/weekN-backend-plan.md` 保留为历史资料，新阶段不继续沿用该命名。

普通周不再额外创建内容重复的实施计划。只有涉及复杂算法、专项架构或跨周迁移时，才创建专项设计/计划，并由执行台账链接；进度状态仍只在执行台账维护。

## 4. 每周执行台账结构

### 4.1 基线

- 实际周编号和路线周次
- 后端分支
- 基准 `dev` 提交
- 产品 PR 和冻结契约路径
- 风险等级
- 本周目标
- 明确不做项
- 环境与真实依赖

### 4.2 当前检查点

放在文件前部，供用户和新 Agent 快速恢复：

- 当前工作块
- 最后完成的工作块和提交号
- 下一步动作
- 当前阻塞
- 需要用户确认的事项
- 恢复命令和必读文档

仅在工作块开始、完成、阻塞或范围变化时更新，不记录每条命令。

### 4.3 工作块总表

每周拆为 3 至 6 块。每块预计 2 至 6 小时，必须产生可验证结果。状态统一为：

```text
PLANNED -> IN_PROGRESS -> VERIFIED
                    \-> BLOCKED
PLANNED ----------------> SKIPPED
```

- `PLANNED`：范围和验证方式已经定义，尚未开始。
- `IN_PROGRESS`：正在修改该块允许的文件。
- `VERIFIED`：完成条件已满足并记录证据。
- `BLOCKED`：无法继续，已记录原因、尝试和所需输入。
- `SKIPPED`：经确认不再需要，必须记录理由，不等同于完成。

同一时间只能有一个 `IN_PROGRESS` 工作块。

### 4.4 工作块执行卡

每块必须包含：

| 字段 | 要求 |
|---|---|
| 目标 | 一句话说明完成后可观察的行为 |
| 业务理由 | 说明它服务哪个周目标或验收场景 |
| 输入与依赖 | 链接契约章节、前序块和环境，不复制整份契约 |
| 修改边界 | 预计修改模块和文件类型，同时列出本块不修改内容 |
| 预期产物 | 代码、迁移、接口、测试、文档或运行证据 |
| 契约影响 | API、MQTT、数据库、权限、缓存、异步、UI 字段逐项说明 |
| 风险与失败表现 | 描述错误可能如何被观察，而不是只写“有风险” |
| 定向验证 | 本块最小测试、人工检查和真实依赖验证 |
| 完成条件 | 可判定的是/否条件 |
| 下一块入口 | 前序条件、用户确认或无阻塞自动进入 |
| 实际结果 | 完成后填写文件、测试结果、偏差、提交号和遗留项 |

工作块不得使用“完善功能”“优化代码”“补充测试”等无法判定完成的表述。

### 4.5 决策与偏差记录

只记录影响范围、契约、数据或后续工作的决定：

- 发现的前提错误或契约冲突
- 选择的方案及未采用方案
- 计划文件与实际文件差异
- 测试策略变化
- 延后事项和指定恢复周

低价值命令输出、正常编译日志和重复解释不进入决策记录。

### 4.6 PR 就绪检查

- 所有计划工作块为 `VERIFIED` 或有批准理由的 `SKIPPED`
- 没有未解释的 `BLOCKED`
- 完整测试只执行一次且结果已记录
- 跳过测试的打包只执行一次且结果已记录
- 高风险真实依赖已验证，或明确列为阻止合并的事项
- 最终差异无秘密、构建产物和无关修改
- 启动、迁移、联调和回滚方法可由队友复现
- PR 文案与台账实际结果一致

## 5. 每周工作流

### 5.1 启动阶段

1. 产品契约冻结并合入 `dev`。
2. 后端从最新 `dev` 创建当周分支。
3. Agent 读取统一入口、治理文档、当周任务、相关契约和后端指南。
4. Agent 检查现有代码和测试，只创建执行台账，不修改业务代码。
5. Agent向用户展示工作块、顺序、风险、预计产物和验证方法。
6. 用户确认后，提交台账并推送分支。
7. 创建一个面向 `dev` 的 Draft PR，作为整周唯一后端 PR。

产品契约未冻结、工作区来源不明或关键字段冲突时，不得进入编码。

### 5.2 工作块循环

每块遵循：

```text
标记 IN_PROGRESS
-> 说明本块目标、文件和验证方法
-> 建立失败用例或现状证据
-> 完成最小实现
-> 运行定向测试
-> 运行必要的相邻回归
-> 自审差异
-> 填写实际结果并标记 VERIFIED
-> 提交并推送
-> 判断下一块阶段门
```

一个提交原则上对应一个完成的工作块。文档修正可与该块一起提交；禁止为制造提交数量拆分无意义提交。

### 5.3 收口阶段

1. 确认所有工作块状态。
2. 执行一次完整后端测试。
3. 执行一次跳过测试的打包。
4. 执行当周要求的真实 MySQL、Redis、MQTT、外部服务或双实例验证。
5. 完成最终差异、凭据、产物和契约漂移检查。
6. 回填执行台账和 Draft PR。
7. 将 Draft PR 转为 Ready for review。

后端 PR 合入 `dev` 后，由前端同步真实接口；三方真实联调前，不把整周标记为完成。

## 6. 混合阶段门

### 6.1 自动继续

当以下条件全部满足时，Agent 完成简短汇报后自动进入下一块：

- 契约已经冻结且实现没有改变契约。
- 工作块属于低或中风险的直接实现。
- 定向测试和相邻回归通过。
- 实际修改没有超出计划模块。
- 下一块输入已经满足。

### 6.2 必须暂停确认

出现以下任一情况，Agent 必须停止相关实现并等待用户明确确认：

- 新增或修改 Flyway 迁移，且尚未展示迁移、保留关系和回滚/恢复方式。
- 修改全局或项目权限边界。
- 引入事务、锁、条件更新、幂等键或并发状态机的重要决策。
- 可能覆盖、删除或不可逆改变真实数据。
- 需要偏离已冻结 API、MQTT、状态枚举或错误语义。
- 需要引入新中间件、大型依赖、微服务或部署组件。
- 测试证明原需求、现有数据或架构前提错误。
- 工作量或影响范围预计超过已确认计划的 25%。
- 需要处理来源不明的未提交修改。

高风险工作块可以在内部先完成不会改变外部状态的调查和测试设计，但不得在确认前执行迁移、破坏性操作或扩大实现范围。

## 7. 用户可见更新

每个工作块固定提供三类信息：

### 开始更新

- 本块要实现的可观察结果
- 预计修改范围
- 契约影响
- 将运行的验证

### 完成更新

- 实际修改
- 测试和人工检查结果
- 与计划的偏差
- 提交号或尚未提交原因

### 下一步更新

- 下一块是什么
- 进入条件是否满足
- 将自动继续还是等待确认

长时间命令只报告有意义的新进展，不重复输出未变化状态。聊天更新保持简短，完整证据写入执行台账。

## 8. 测试策略与停止规则

### 工作块内

1. 用失败测试或可复现现状证明风险存在。
2. 完成最小实现。
3. 只运行覆盖当前风险的定向测试。
4. 运行受影响的相邻回归。
5. 满足完成条件后停止，并记录结果。

### PR 前

- 完整后端测试一次。
- `-DskipTests` 打包一次。
- 按风险进行一次真实依赖验证。
- 代码、配置、依赖和输入未变化时，不重复全量测试。

测试失败后必须先解释根因并修改代码、配置、数据或测试；不得原样重复执行以期待偶然通过。随机、并发和压力测试必须有固定边界、超时和停止条件。

## 9. Draft PR 与提交策略

- 每周仍只有一个后端 PR。
- 第一次推送内容是经用户确认的执行台账，随后创建 Draft PR。
- 每个已验证工作块产生一个有意义提交并推送到同一分支。
- Draft PR 描述顶部显示当前工作块和完成比例，并链接执行台账。
- 高风险阶段门在 PR 中保留明确检查项。
- 只有 PR 就绪检查通过后才转为 Ready for review。
- GitHub 不可访问时，本地提交和台账继续作为事实源；恢复网络后按原提交顺序推送，不用重新生成过程。

## 10. 效率边界

- 每周最多 6 个工作块，防止把管理本身变成主要工作。
- 执行台账只在检查点更新，不记录逐行编码过程。
- 每块完成证据优先使用测试名称、通过数量、关键响应和提交号，不粘贴完整日志。
- Agent 恢复时先读取当前检查点、当前块和其直接引用，再按需读取代码，不默认重扫全部文档。
- 产品契约字段只链接，不在执行台账复制维护。
- 同一结果只保留一个权威位置：范围在周文档，字段在契约，执行状态在台账，系统现状在 `CURRENT_STATE`。

## 11. 示例工作块

```markdown
### B2：实现当前角色鉴权

- 状态：PLANNED
- 预计工时：4 小时
- 目标：受保护请求按数据库当前角色判定权限，角色变化在下一次请求生效。
- 输入：AUTH_WORKBENCH_V1 §4、B1 角色迁移 VERIFIED。
- 修改边界：鉴权服务、拦截器、请求上下文和对应测试；不修改接口路径和角色枚举。
- 预期产物：角色查询、权限注解、401/403 响应及测试。
- 契约影响：权限实现；API 响应遵循已冻结契约；MQTT 无变化。
- 风险：读取 Token 角色会导致权限无法即时收回；线程上下文未清理会串请求。
- 验证：角色提升、角色移除、账号禁用、权限不足和线程上下文清理测试。
- 完成条件：全部定向测试通过，未依赖 JWT 角色声明，差异未超出修改边界。
- 下一块入口：VERIFIED 后自动进入 B3；若需要修改权限矩阵则暂停确认。
- 实际结果：完成后填写。
```

## 12. 验收标准

制度落地后，任选一周后端任务应能够证明：

1. 编码前已经存在用户确认的工作块计划。
2. 用户可从台账顶部在一分钟内判断当前进度和阻塞。
3. 每个工作块都有可判定结果、验证证据和提交。
4. 高风险决定没有在用户不知情时越过阶段门。
5. Agent 中断后可以从当前检查点继续，而不需要重新规划整周。
6. PR 评审者可以从提交和台账追溯每项实现。
7. 完整测试和打包没有因缺乏信心而被无意义重复。
8. 文档维护时间保持在每周总开发时间的约 10%，没有取代真实实现。
