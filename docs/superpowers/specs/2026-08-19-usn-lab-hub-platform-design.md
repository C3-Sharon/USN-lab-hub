# USN Lab Hub 六个月完整建设总体设计

> 状态：方案已确认，进入分阶段实施规划
> 日期：2026-08-19  
> 基线：`origin/dev`，commit `4930b3a`  
> 建设周期：26 个开发周；三人每周各投入约 12-20 小时  
> 产品定位：面向中国高校小型硬件实验室的项目协作、学习实验、资源管理、设备运维与知识传承平台

## 1. 文档目的

本文定义 USN Lab Hub 在现有人员、考勤和 PM-001 IoT 闭环基础上的六个月完整建设目标。它同时约束产品、前端、Java 后端、RAG、Agent、部署、测试和三人协作方式。

本文不是“愿望清单”，也不是只用于起步的 MVP 说明。六个月结束时，团队只能在本文第 18 节的完整成品验收矩阵通过后，声明本阶段完成。若某项未完成，应如实标记范围缺口，不得通过改名、隐藏入口或降低文档口径把半成品描述为完整成品。

当前已经验证的基线能力包括：

- 成员登录、角色、成员管理和考勤基础能力。
- PM-001 MQTT telemetry 上报、原始数据和指标数据持久化。
- latest、history、阈值告警、规则建议、指令、ACK 和操作日志。
- 设备健康评分、公开展示和登录后 IoT 总览。
- SSE 最新遥测推送、断线重连与轮询降级。

下一阶段不重写已经通过验收的闭环，而是把单设备演示抽象为可持续使用的平台能力。

## 2. 核心决策

1. 以项目工作台为产品主轴，个人首页同时展示考勤。
2. 正式项目可以不接入 IoT；IoT 是硬件项目的可选增强能力。
3. 学习实验台与项目工作台并列，分别服务零基础学习和正式项目/竞赛。
4. 元器件、模块、开发板、实验室资产和自研硬件采用不同的管理粒度。
5. 自研硬件使用“产品 -> 版本 -> BOM -> 裸板批次 -> 装配工单 -> 板卡实例”模型。
6. 采购采用可选审批的轻量闭环，不建设完整 ERP、会计和报销系统。
7. 知识库支持持续增删改查、审核发布、版本、增量索引、删除和恢复。
8. RAG 先在主项目中按可抽取边界实现，两个真实场景通过评测后再提取 Maven 框架。
9. Agent 采用统一入口和专业模式；硬件控制必须经过后端受控工具、权限和风险校验。
10. 后端采用模块化单体和可选外部 Worker，不用微服务数量证明技术水平。
11. 真实部署使用一台实验室服务器、Nginx 和两个 Spring Boot 实例；不宣称物理高可用。
12. 日常服务小实验室真实规模，使用模拟器验证一万设备模型和 1,000-3,000 条遥测/秒。
13. 六个月中每个角色每周形成一次有意义、可审查的 PR 交付，月底发布稳定版本。
14. UI 使用“实验室工作台 + 少量电子工程元素”，不采用通用 GPT/AI 营销风格。

## 4. 用户与权限模型

采用“全局角色 + 项目角色 + 资源归属 + 风险等级”的授权方式。

全局角色：

- 系统管理员：账号、系统配置、全局权限和安全设置。
- 老师/实验室负责人：查看全部项目、人员、资源和统计。
- 库存管理员：采购入库、库存盘点、条件审批和库存修正。
- 普通成员：考勤、学习实验、参与项目、申请资产和领用物料。
- 访客：只访问显式公开的项目成果和媒体。

项目角色：

- 项目负责人：项目设置、成员、资料、设备和公开范围。
- 项目维护者：任务、文档、实验记录和设备运维。
- 项目成员：执行任务、提交记录和申请资源。
- 项目观察者：只读查看。

硬件控制权限必须同时满足：用户全局权限、项目成员关系、设备归属、指令白名单、风险等级和审批策略。

## 5. 工作台、项目与学习实验

### 5.1 个人工作台

个人工作台是登录后的默认入口，第一屏包含：

- 今日考勤状态、签到/签退入口和异常提示。
- 进行中的项目、角色、当前里程碑、进度和设备状态。
- 本周任务：待开始、进行中、待验收、已完成。
- 实验室动态、待审批事项和设备告警。
- 作为次级区域出现的实验室助手，不以聊天框主导页面。

老师、项目负责人和普通成员看到的数据范围不同，但页面骨架一致。

### 5.2 项目工作台

项目状态为：`PREPARING -> ACTIVE -> PAUSED -> COMPLETED -> ARCHIVED`。

项目包含基本信息、成员、里程碑、轻量任务、动态、仓库、实验、文档、硬件、设备、成果和交接。任务状态为待办、进行中、阻塞、已完成、已取消。任务可关联成员、里程碑、实验、硬件版本、设备实例、物料申请、知识条目和代码仓库。

GitHub 和实验室 GitLab 均提供个人连接入口和项目级只读连接。个人连接用于身份和贡献映射；项目连接用于稳定同步仓库摘要。GitLab 不可达时显示最后成功同步时间，不能拖垮项目工作台，也不能把网络不可达误报为 Token 失效。

### 5.3 学习实验台

学习实验台服务从电路基础、焊接、STM32/ESP32、传感器、通信协议、原理图和 PCB 到完整联网硬件的学习过程。

```text
学习路线 -> 实验模板 -> 个人实验 -> 过程记录 -> 导师反馈
                                      -> 能力证据
                                      -> 可转项目草案
```

实验记录采用固定核心字段、JSON Schema 扩展字段和模板版本。项目负责人或维护者可复制系统模板并配置本项目模板。模板变更生成新版本，不破坏旧记录。已发布实验记录的修改形成内容版本。

结构化实验至少支持：目的、硬件版本、设备实例、BOM/固件版本、环境、参数、步骤、结果、异常、结论、附件和遥测区间快照。

## 6. 元器件、采购、库存与资产

### 6.1 对象分类

- 元器件：电阻、电容、芯片、传感器、连接器等，按数量和批次管理。
- 模块/开发板：可按库存数量管理，也可按价值和复用性转为独立资产。
- 实验室资产：示波器、焊台、功耗表和边缘终端，按独立编号借用和维护。
- 自研硬件：按产品、版本和板卡实例管理。

### 6.2 元器件目录与联网搜索

元器件目录支持 CRUD、分类、型号、厂商、封装、规格、单位、数据手册和图片。联网搜索用于辅助填写厂商、封装、关键电气参数、数据手册和替代料。外部结果必须人工确认，并保存来源和查询时间；外部服务不可用时可以手工录入。

库存事实、外部规格快照和智能替代建议必须分层保存。替代料不得未经确认自动替换 BOM。

### 6.3 轻量采购闭环

采购状态：

```text
DRAFT -> PENDING_APPROVAL -> APPROVED -> ORDERED
      -> PARTIALLY_RECEIVED -> RECEIVED -> COMPLETED
异常：REJECTED / CANCELED / PARTIALLY_RETURNED / RETURNED
```

采购单记录订单编号、平台订单号、供应商、购买人、时间、金额、运费、优惠、实付、发票、经费来源、关联项目和明细。小额普通采购可跳过审批；超阈值、贵重和指定类别必须审批。

一单可包含多种物料并分批到货。只有确认到货入库才能增加库存：

```text
采购明细 -> 到货记录 -> 库存批次 -> 库存增加流水
```

入库操作必须有幂等键和唯一约束，禁止重复点击导致重复加库存。发票默认仅购买人、项目负责人、库存管理员和老师可见。

### 6.4 领用与库存一致性

普通且库存充足的低价值物料可直接领用；贵重、库存紧张或超数量阈值时生成审批和库存预占。审批通过后扣减，拒绝或超时释放预占。

库存数量不能由页面直接修改。入库、领用、退回、损耗、报废和盘点修正都必须通过库存流水命令完成，并记录原因、操作者和关联业务。

### 6.5 资产借用

实验室资产记录独立编号、类型、位置、状态、责任人、购买来源、图片、借用和维护。资产借用与元器件消耗分开：资产需要归还，元器件通常进入消耗或剩余退回。

## 7. 自研硬件、打板与装配追溯

```text
项目
└─ 硬件产品
   └─ 硬件版本
      ├─ BOM 版本
      ├─ 原理图/PCB/固件
      ├─ PCB 打板单
      │  └─ 裸板批次/可选裸板实例
      └─ 装配工单
         └─ 板卡实例
```

PCB 打板单记录厂家、订单号、下单时间、Gerber/BOM/坐标文件版本或哈希、板层、板厚、铜厚、表面工艺、数量、金额、发票、到货和质检。打板单必须关联项目和硬件版本。

裸板序列化由项目或硬件版本配置。默认裸板按批次管理，装配完成后生成独立板卡编号；竞赛、贵重或关键板可以从到货开始逐块编号。序列化策略在打板单进入已下单状态后冻结。

装配工单记录硬件版本、裸板批次、BOM 快照、计划数量、焊接人、时间和实际领料。实际消耗必须追溯来源库存批次、替代料、损耗和对应板卡实例。返修和芯片更换继续通过维修工单扣减库存。

每块成品板能够追溯项目、硬件版本、裸板批次、装配工单、物料批次、固件版本、测试、维修和 IoT 身份。系统可计算项目采购金额、版本打板成本、单板估算成本以及 BOM 计划与实际消耗差异，但不提供会计核算。

## 8. IoT 平台化

现有 PM-001 闭环保留并泛化为设备模板和设备实例能力。设备可配置仅登记、可借用、可维护、可采集数据和可远程控制等能力。

IoT 模块支持：

- 多项目、多设备和动态指标定义。
- 设备凭据、Topic 模板和 payload 版本。
- telemetry/status/command/ack。
- 原始消息留证、结构化指标、latest、history 和 SSE。
- 阈值/离线告警、规则建议、指令状态机和审计。
- 模拟器与真实硬件使用相同契约。

消息使用设备编号、消息 ID 和协议版本进行校验。重复上报、重复 ACK 和乱序消息必须有明确策略。设备控制不允许模型直接访问 Broker。

## 9. 媒体与文件

项目、硬件产品/版本、设备资产、板卡实例、元器件、采购、到货、实验和维修均可关联图片或文件。上传不是创建项目或入库的强制条件。

- 项目支持可选封面和相册。
- 元器件支持目录标准图和入库批次实物图。
- 硬件版本支持 PCB 正反面、结构图和版本演进图。
- 资产和实例支持实物、铭牌、损坏和维修前后照片。
- 采购支持订单截图、发票、到货和包装照片。

无图片时按项目类别、元器件封装、资产类型和硬件状态显示确定性占位 UI；不在运行时调用 AI 生成占位图。

原图保存到 MinIO，数据库保存媒体元数据。系统生成缩略图和 WebP 展示版本、校验类型和大小、使用哈希去重并移除不必要的 EXIF 定位信息。图片默认继承所属对象权限；只有显式标记可公开的图片进入成果页。

## 10. 总体技术架构

采用模块化单体、可选外部 Worker 和双应用实例：

```text
Nginx
├─ Vue 3 静态前端
├─ Spring Boot 实例 A
└─ Spring Boot 实例 B
   ├─ identity / attendance
   ├─ project / learning
   ├─ procurement / inventory / asset
   ├─ hardware / iot
   ├─ knowledge / agent
   ├─ integration / media
   └─ audit / notification

MySQL        业务事实、事务、权限、状态和 RAG 元数据
Redis        热点缓存、幂等短状态、限流和分布式协调
MQTT Broker  设备 telemetry、command 和 ACK
ES/OpenSearch 全文、向量和混合检索派生索引
MinIO        原始文件、图片、发票、手册和实验附件
Model Adapter 外部 API 与本地模型切换
Optional Worker 复杂解析、OCR、Embedding 或重排
```

Controller 不直接访问基础设施。模块通过应用服务和受控领域事件协作。跨模块强一致操作使用本地事务；外部系统和异步副作用使用 Outbox、幂等消费和补偿。

不在当前阶段拆微服务。只有出现独立扩缩容、故障隔离、特殊运行环境或独立发布的真实需要时才重新评审。

## 11. Java RAG Kernel 与 Agent

### 11.1 知识范围和可信度

知识可关联实验室、项目、学习路线、硬件产品、硬件版本、设备实例和元器件。类型包括数据手册、原理图、PCB/固件说明、实验记录、故障案例、维修记录、竞赛规则和项目交接。

可信度顺序为：已审核实验室知识、官方数据手册、项目正式文档、未审核实验记录、外部联网候选、Agent 推断。回答必须标明来源类型。

### 11.2 摄取和版本

```text
UPLOADED -> VALIDATING -> PARSING -> NORMALIZING
         -> CHUNKING -> EMBEDDING -> INDEXING -> RETRIEVAL_READY
```

修改创建新 ResourceVersion。新版本全部成功后原子切换 ACTIVE，失败时旧版本继续服务。删除先禁止检索，再异步清理索引和文件。MySQL 是知识元数据和状态事实源；检索索引可以重建。

### 11.3 检索

```text
权限与范围 -> 意图 -> BM25 + Dense -> RRF
           -> 可选 Reranker -> Context Assembly
           -> 模型回答 -> Citation Validator -> Retrieval Trace
```

第一批评测覆盖元器件参数、实验复现、故障诊断、项目交接、无答案、冲突和越权泄漏。原始遥测不整体向量化；Agent 通过受控工具查询实时数据，再与文档证据组合。

### 11.4 框架提取门槛

先在主项目内建立 `rag-kernel-core`、ingestion、retrieval、citation、evaluation 和 Spring Adapter 边界。只有元器件手册问答和设备故障诊断均通过固定评测集，才提取独立 Maven 模块供 agentPlatform 和其他项目使用。边界未稳定时不得为“框架感”强拆仓库。

### 11.5 Agent

统一助手提供学习辅导、项目协作、元器件查询、设备诊断和受控硬件调控模式。工具权限与模式隔离。

```text
Agent 建议 -> 结构化 Tool Call -> 权限/设备范围
           -> 参数白名单 -> 风险等级 -> 人工确认或低风险策略
           -> 幂等下发 -> ACK/超时 -> 审计和反馈
```

RAG 提供证据，不承担控制授权；检索到的文档和网页永远不能触发工具调用授权。

## 12. Java 工程能力落点

| 能力 | 真实场景 | 设计方式 |
|---|---|---|
| 事务/一致性 | 采购入库、库存预占、装配扣料 | 条件更新、唯一键、本地事务、库存流水 |
| 乐观锁/CAS | 审批、任务、指令状态 | version 或旧状态条件更新 |
| 幂等 | MQTT、ACK、Webhook、重复提交 | 业务幂等键、唯一索引、结果复用 |
| 多线程 | 遥测、摄取、Git 同步 | 有界隔离线程池、超时、拒绝和背压 |
| 最终一致性 | DB 成功但索引/通知失败 | Transactional Outbox、重试和补偿 |
| 缓存 | 工作台、latest、权限、外部搜索 | Cache Aside、TTL 抖动、版本失效 |
| 分布式协调 | 双实例调度和超时扫描 | 租约锁或数据库抢占；关键事实不依赖锁 |
| 大表 | 遥测、审计、库存流水 | 组合索引、游标分页、冷热归档，按压测决定分区 |
| 大 Key | 项目摘要、设备集合、订阅 | 拆 Key、限制集合、禁止缓存完整大页面对象 |
| 容灾 | Redis/检索/模型/GitLab/Broker | 降级、快照、重试、熔断和部分成功 |

SSE 跨实例可用 Redis Pub/Sub 广播瞬时事件，前端通过 latest 恢复遗漏；库存、审批、指令和采购事件不得只依赖 Pub/Sub。

## 13. UI 设计和无 Figma 实施方法

视觉方向为“85% 克制实验室工作台 + 15% 电子工程特征”。品牌采样色：感知蓝约 `#0B6DB6`，互联紫约 `#93559C`，过渡靛蓝约 `#6365A9`。蓝色承担主交互，紫色仅用于知识和 Agent。

禁止巨大渐变标题、玻璃拟态、发光边框、营销 Hero、卡片嵌套、夸张圆角、满屏胶囊标签和聊天框主导首页。圆环用于进度和健康，感知波纹用于设备状态，PCB/设备缩略图和版本编号用于硬件辨识。

视觉参考：

- `docs/design/reference/personal-workbench-v1.png`
- `docs/design/reference/usn-lab-emblem-reference.png`

## 14. 安全、可观测与恢复

- Token、模型密钥和第三方凭据加密保存并脱敏输出。
- RAG 在检索前执行 ACL；外部文档不能成为系统指令。
- 联网元器件搜索通过受控出站网关，限制协议、目标、重定向、大小和超时。
- 上传校验类型、大小和哈希；成熟阶段增加恶意文件扫描。
- 权限、采购、库存、知识发布和硬件控制全部审计。
- Actuator + Micrometer + Prometheus + Grafana 观察接口、线程池、连接池、MQTT、缓存、任务和 RAG。
- Trace ID 串联 HTTP、异步任务、MQTT、RAG 和 Agent Tool。

恢复目标：重要数据 RPO 不超过 24 小时，普通故障 RTO 不超过 4 小时。MySQL 和 MinIO 每日备份并定期恢复验证；ES/OpenSearch 是可重建派生索引；Redis 不保存无法从事实源恢复的数据。

## 16. 三人职责与周度协作

### 16.1 产品负责人

负责用户流程、字段字典、原型、权限、学习路线、实验模板、采购/库存规则、硬件组协调、RAG 黄金评测、Agent 安全用例、周验收、老师材料和最终产品叙事。产品 PR 不是散文总结，而是冻结可验收契约和样例。

### 16.2 前端兼边缘工具负责人

负责 Vue 页面、设计 Token、权限路由、状态和错误体验、E2E、Playwright 截图、RAG Inspector、Agent 审批交互，以及 Python/C++ 设备模拟器、硬件接入示例和压力数据生成器。

### 16.3 Java 后端负责人

负责模块边界、Flyway、API、权限、采购库存事务、硬件追溯、MQTT、缓存、异步任务、RAG Kernel、Agent Tool、双实例、监控、压测、容灾和备份。

### 16.4 每周节奏

- 周一：产品冻结本周场景、契约、样例、范围和风险。
- 周二至周三：前后端并行；前端按契约 mock，后端实现真实接口。
- 周三或周四：契约测试和首次真实联调。
- 周四：各角色提交主 PR，完成自测和自审。
- 周五/本周最后工作日：评审、修正、合并 `dev`、完整场景验收和状态文档更新。

字段或协议变化时，合并顺序通常为产品 -> 后端 -> 前端；无契约变化时允许并行，但最终前端必须同步最新后端 `dev` 做真实联调。

## 18. 测试策略、效率和停止条件

### 18.1 风险分级

- 低风险：文案、纯展示、无共享状态。执行定向测试、构建和页面检查。
- 中风险：普通 CRUD、筛选、文件元数据。执行单元、数据库集成、契约和相邻回归。
- 高风险：库存、权限、MQTT、指令、RAG ACL、Flyway、异步一致性。执行真实服务集成、并发、失败路径、回归和人工检阅。

### 18.2 节点化测试

- 编码中：只运行受影响模块的最快测试。
- PR 前：模块测试、契约测试、构建和静态自审。
- 合入 `dev` 后：完整场景联调和必要 E2E。
- 月度发布：全量回归、备份恢复抽查和演示脚本。
- 第 12、21、25 周：并发/性能专项。
- 第 25-26 周：故障、双实例、恢复和完整验收。

### 18.3 UI 检阅

关键页面必须在 `1440x900`、`1280x800` 和 `390x844` 截图检查：布局比例、文字溢出、对齐、密度、空状态、错误状态、权限状态和交互反馈。首个个人工作台对照参考图至少迭代一轮。

视觉回归使用允许抗锯齿差异的截图比较和人工检查，不使用整张截图文件哈希完全相等作为 UI 正确性的判断。

### 18.4 防止无穷测试

禁止在没有代码、配置、依赖或测试数据变化时重复运行同一全量测试。禁止为了得到更多“通过次数”重复执行已经稳定通过的套件。

哈希、幂等和版本逻辑使用固定代表性用例：相同输入、变化输入、非法输入和必要边界。除非属于安全专项且有时间预算，不做无界随机碰撞或无限 fuzz。任何 fuzz/随机测试必须固定 seed、最大样本数和最长运行时间。

测试完成条件：

1. 需求验收场景有直接证据。
2. 改动行为有自动化测试或明确人工检阅。
3. 受影响的相邻回归通过。
4. 没有未解释的失败、跳过或数据污染。
5. 继续测试不会覆盖新的风险类别。

满足以上条件后停止测试并提交结果。若失败重复出现，应先定位根因，不通过不断重跑期待偶然成功。

### 18.5 RAG 与性能测试

RAG 使用版本化黄金问题集，指标包括 Recall@K、MRR/nDCG、引用正确性、Faithfulness、无答案识别、权限泄漏、p95 和成本。每次实验只改变一个主要变量。

性能报告必须记录机器、数据量、脚本、持续时间、吞吐、错误率、平均、p95、p99 和资源使用。真实目标是小实验室稳定使用；一万设备为模拟验证，不宣传为真实在线规模。

## 20. 风险与重新评审门

- 若第 10 周库存事务仍不稳定，暂停新增资产能力，先修复一致性。
- 若第 17 周仍存在 PM-001 硬编码，暂停新增 Agent 功能，先完成 IoT 泛化。
- 若第 21 周两个 RAG 场景未通过评测，不提取独立框架，也不引入 GraphRAG。
- 若单服务器资源不足，优先降低非关键 Worker 并发和模型本地化，不拆分微服务。
- 若 GitLab 长期不可达，保留手动同步和最后快照，不阻塞平台主体。
- 若真实硬件配合不足，模拟器只能作为契约和压测兜底；最终验收仍要求至少三类真实硬件。
- 若开发进度偏慢，减少装饰性统计、复杂筛选和次要自动化，不删除最终矩阵中的业务主链路。
