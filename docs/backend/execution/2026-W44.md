- 状态：PLANNED
- 预计工时：5-7 小时
- 目标：提供供应商无关的媒体存储端口和安全的本地单实例实现。
- 业务理由：业务层需要稳定 mediaId，同时不能绑定最终对象存储产品或信任用户文件。
- 输入与依赖：冻结媒体字段、本地文件配置、Java ImageIO；不新增图片或对象存储依赖。
- 修改边界：新增 MediaStoragePort、本地适配、staging/commit/open/rollbackNewObject、图片检查与重编码；不实现业务图库 API。
- 预期产物：随机内部键、目录边界检查、JPEG/PNG 魔数/MIME/扩展名/尺寸/大小验证、去元数据展示文件、存储单元测试。
- 契约影响：API 暂无；内部存储键永不进入 VO；数据库无新迁移；权限由 B5 接入。
- 风险与失败表现：路径穿越、伪装文件、超大像素、元数据残留、错误回滚删除已有对象、临时文件泄漏。
- 定向验证：真实 JPEG/PNG、伪装脚本、错误扩展名、超限尺寸、原子移动失败、重复键和 staging 清理。
- 人工验证：检查仓库外配置目录，不写入构建产物或用户提供文件名。
- 完成条件：存储端口不暴露供应商字段；合法图片可安全往返；非法文件被拒绝；回滚只删除本次新对象。
- 下一块入口：B4 VERIFIED 后暂停报告存储与补偿实际行为，再进入 B5。
- 已批准设计：
  - 使用 JDK 17 `ImageIO` 和供应商无关 `MediaStoragePort`，不新增图片或对象存储依赖；本地实现根目录为 `${USNHUB_MEDIA_ROOT:${user.home}/.usn-lab-hub/media}`。
  - 根目录固定划分 `staging/original/display`；应用启动时清空 staging。原始文件保持原字节，展示文件由解码后的新 `BufferedImage` 按原 JPEG/PNG 格式重新编码，不复制原元数据。
  - `stage` 流式写临时文件并计算原件大小和 SHA-256；超过 5 MiB 立即失败并删除临时文件。`commit` 使用随机 UUID 逻辑对象键提交原件和展示文件；`open` 只接受受控逻辑键；`rollbackNewObject` 只接受本次 commit 返回的句柄。
  - 校验顺序固定为大小、扩展名/MIME/魔数一致性、读取宽高、完整解码、重新编码。仅接受 `.jpg/.jpeg + image/jpeg` 和 `.png + image/png`，宽高均为 1-4096；拒绝 SVG、GIF、WebP、损坏图片、伪装脚本、绝对路径、路径穿越和未知键前缀。
  - 原件和展示文件提交是两个文件操作：第二次移动失败时立即删除第一次移动的新文件并清理 staging；数据库后续失败由 B5 调用 `rollbackNewObject`。不删除既有对象，不实现后台物理清理。
  - B4 只暴露内部存储/处理异常；B5 接入业务 API 时映射冻结的 `MEDIA_*` reason。定向测试使用固定生成的真实 JPEG/PNG、固定非法样本和可注入的移动失败点，不做无界随机或重复全量测试。
- 实际结果：尚未开始。
