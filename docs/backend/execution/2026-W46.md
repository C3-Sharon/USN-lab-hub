## 4. B1 V14 迁移方案（待用户批准）

### 4.1 新建表

1. `lab_inventory_issue_policy_version`：不可变策略版本，唯一 `policy_version`。
2. `lab_inventory_issue_policy_forced_category`：策略与强制审批分类复合主键。
3. `lab_inventory_issue_policy_component_override`：`(policy_id, component_id)` 唯一，冻结名称、单位和直接数量上限。
4. `lab_inventory_issue_request`、`lab_inventory_issue_line`：七态申请、版本、金额和元器件快照；同申请行号、元器件分别唯一。
5. `lab_inventory_issue_approval_record`：追加写审批事实和触发快照。
6. `lab_inventory_reservation`、`lab_inventory_reservation_allocation`：每申请行一份主预占，`(reservation_id,batch_id)` 唯一。
7. `lab_inventory_fulfillment`、`lab_inventory_fulfillment_line`：每申请最多一份发放事实，行固定关联 allocation、batch 和 movement。
8. `lab_inventory_return`、`lab_inventory_return_line`：退回状态、版本和原发放行引用。
9. `lab_inventory_write_off_command`：LOSS/SCRAP 不可变命令及唯一 commandNo/movement 关联。

审计复用现有 `lab_procurement_audit_log`（其 V13 定义已覆盖 procurement and inventory），幂等复用 `lab_request_idempotency`，避免重复建设平行事实表。

### 4.2 修改现有表

- `lab_component_inventory_balance`：新增 `reserved_quantity DECIMAL(19,3) NOT NULL DEFAULT 0.000`；重建数量 CHECK 为 `on_hand_quantity >= reserved_quantity AND reserved_quantity >= 0`。
- `lab_inventory_batch`：新增相同 `reserved_quantity`；重建数量 CHECK，保证 `initial_quantity > 0`、`current_quantity >= reserved_quantity >= 0`、`current_quantity <= initial_quantity`；不增加 version。
- `lab_inventory_movement`：新增可空 `reason VARCHAR(500)`；删除并重建 movementType、sourceType、数量方向 CHECK；唯一索引改为 `(movement_type,source_type,source_id,batch_id)`。

### 4.3 索引与数据保留

- 批次选择索引：`(component_id,status,expiry_date,create_time,id)`，服务 FEFO 后 FIFO 的稳定锁定顺序。
- 申请列表按 requester/project/status/update_time/id 建稳定分页索引；预占按 status/expires_at/id 支持有界过期扫描。
- 创建新流水唯一索引前，先查询 V13 历史事实是否存在重复组合；发现异常即使迁移失败，也禁止删除、合并或静默改写历史流水。
- 新增 reserved 列默认 0，不回填其他值；迁移前后逐项比较采购单、到货、批次、余额、流水、媒体和 PM-001 事实。

### 4.4 恢复边界

- 不提供破坏性 down migration；旧应用应忽略 V14 新表和新增列。
- MySQL DDL 不能假定整体事务回滚。只在隔离 schema 先验证；共享环境迁移前备份并记录 Flyway 状态，失败时停止应用启动并按备份/干净 schema 恢复，不手工跳过失败版本。
- V14 不修改 V13 文件，不覆盖 `PROCUREMENT_RECEIPT_IN`，不改变媒体 ACL、MQTT、知识、RAG 或 Agent。
