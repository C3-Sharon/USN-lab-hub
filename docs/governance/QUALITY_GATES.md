# 质量门禁与测试停止规则

## 1. 风险分级

| 等级 | 示例 | PR 前要求 | 合入 dev 后要求 |
|---|---|---|---|
| 低 | 文案、静态展示、无共享状态 | 定向检查、构建、页面人工检查 | 相邻页面冒烟 |
| 中 | 普通 CRUD、筛选、文件元数据 | 单元、数据库集成、API 契约、构建 | 真实前后端主流程和错误态 |
| 高 | 权限、库存、MQTT、指令、Flyway、RAG ACL、异步一致性 | 单元、真实数据库/服务集成、并发或失败路径、契约、回归 | 完整场景、审计、人工检阅和恢复/降级证据 |

风险由影响的数据和行为决定，不由改动行数决定。产品周文档必须标出风险等级。

## 2. 角色完成定义

### 产品

- 用户、前置条件、主流程、异常流程、权限和不做项明确。
- 字段有名称、类型、必填、样例、单位、枚举和错误语义。
- 至少一个正常样例、一个空状态、一个失败样例。
- 验收步骤可由没有参与编写的人执行。
- 影响现有契约时更新生效文档并声明兼容策略。

### 前端与边缘工具

- mock 与生效 API/MQTT 契约字段完全一致。
- loading、empty、error、permission、success 状态完整。
- 真实 API 联调后不保留默认启用的业务 mock。
- 关键页面通过 `1440x900`、`1280x800`、`390x844` 截图检阅。
- 页面无文字溢出、无不合理重叠、无嵌套卡片和布局跳动。
- 模拟器有固定 seed、速率上限、退出方式和示例命令。

### Java 后端

- Controller 不直接访问 Mapper 或外部基础设施。
- 写操作明确事务边界、权限、幂等、状态前置条件和审计。
- 数据库变化只用新的 Flyway 迁移，不修改已在共享环境执行的迁移。
- DTO/VO 有校验和稳定字段，错误响应有明确错误码或语义。
- 新线程池有界，包含命名、队列、拒绝、超时和指标。
- 缓存可从事实源恢复，不能成为库存、审批或指令唯一事实。
- 高风险行为包含并发、重复请求、失败和回滚测试。

## 3. 后端工作块门禁

后端工作块只有同时满足以下条件，才能从 `IN_PROGRESS` 标记为 `VERIFIED`：

1. 产生了执行台账中定义的可判定结果，没有用计划内容代替实际结果。
2. 新增或修改行为有直接的自动化测试，或有说明理由的人工检阅证据。
3. 受影响的相邻行为完成必要回归。
4. 已检查本块差异，没有超出确认过的文件和契约边界。
5. 测试、人工检查、实际文件、偏差和遗留项已回填执行台账。
6. 没有未解释失败、跳过、资源泄漏、数据污染或阻塞。

普通低、中风险工作块满足以上门禁后，可以完成更新并自动进入下一块。以下高风险设计必须先向用户展示方案和影响，取得明确确认后才能执行会改变代码、数据库或外部状态的操作：

- Flyway 迁移及数据保留、恢复方案。
- 全局或项目权限边界变化。
- 事务、锁、条件更新、幂等键和并发状态机。
- 覆盖、删除或不可逆的真实数据操作。
- API、MQTT、状态枚举或错误语义偏离生效契约。
- 新中间件、大型依赖、微服务或部署组件。
- 测试推翻需求、数据或架构前提。
- 影响范围超过确认计划的 25%，或遇到影响任务的来源不明改动。

高风险 PR 转为 Ready for review 前，必须包含对应的真实 MySQL、Redis、MQTT、外部服务、并发或双实例证据。缺少凭据或基础设施时应保持明确阻塞，不得以 H2、mock、计划步骤或口头说明冒充真实验证。

工作块内测试达到本文件“防止无穷测试”的五条停止条件后必须停止。完整后端测试只在 PR 就绪前执行一次，随后执行一次跳过测试的打包；代码、配置、依赖和输入未变化时不重复全量套件。

## 4. 测试节点

1. 编码中只运行最小受影响测试。
2. 单个任务结束运行该模块测试并提交。
3. PR 前运行模块测试、契约检查、构建和静态自审。
4. 合入 `dev` 后运行完整业务场景和必要 E2E。
5. 稳定版本运行全量回归、演示脚本和备份恢复抽查。
6. 第 12、21、25 周分别做库存并发、RAG 评测、系统性能与恢复专项。

基线命令：

```bash
cd backend
./mvnw test
./mvnw -DskipTests package

cd ../frontend
npm ci
npm run build
```

Windows 将 `./mvnw` 替换为 `mvnw.cmd`。若 package scripts 增加 `test`、`lint` 或 `test:e2e`，本文件和 README 必须同步。

## 5. UI 检阅表

- 品牌蓝只承担主交互，紫色只用于知识/Agent 等少量语义。
- 页面是工作台而非营销首页，没有巨大 Hero、玻璃拟态和发光装饰。
- 卡片圆角不超过 8px，页面分区不做漂浮卡片，卡片不嵌套卡片。
- 表格、筛选、详情、批量操作适合重复工作，不用装饰抢占首屏。
- 项目、元器件、硬件和资产图片可选；无图占位具有对象类型辨识度。
- 交互控件使用 Element Plus 或 Lucide 图标，陌生图标有 tooltip。
- 三个固定视口截图和关键弹窗截图进入 PR 证据。
- 人工对照参考图检查层级、密度、对齐和留白。

截图比较允许字体渲染和抗锯齿差异，不能只比较整图哈希。

## 6. 防止无穷测试

禁止：

- 代码、配置、依赖、数据未变化时重跑同一全量套件。
- 为增加“通过次数”重复稳定测试。
- 无界随机碰撞、无限 fuzz 或没有超时的压测。
- 测试失败后反复重跑期待偶然成功。

随机或 fuzz 测试必须固定 seed、最大样本数和最长运行时间。哈希、幂等和版本逻辑使用四类固定用例：相同输入、变化输入、非法输入、必要边界。

满足以下五点后停止测试并提交：

1. 验收场景有直接证据。
2. 新增或修改行为有自动化测试或明确人工检阅。
3. 受影响相邻回归通过。
4. 无未解释失败、跳过、资源泄漏或数据污染。
5. 继续运行不会覆盖新的风险类别。

## 7. 性能与 RAG 报告

性能报告必须记录机器、版本、数据量、脚本、持续时间、吞吐、错误率、平均、p95、p99、CPU、内存、数据库和线程池状态。一万设备是模拟模型，不表述为真实在线规模。

RAG 每次实验只改变一个主要变量，记录数据集版本、索引版本、模型、参数、Recall@K、MRR/nDCG、引用正确性、忠实度、无答案识别、权限泄漏、p95 和成本。未通过固定评测不得只用“回答看起来不错”验收。
