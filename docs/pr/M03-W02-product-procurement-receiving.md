## 核心一致性边界

- 确认到货是唯一增加库存的业务动作。
- 到货事实、库存批次、增加流水、余额和采购进度在一个数据库事务内提交。
- 任一超量、冲突或内部失败必须整体回滚。
- 精确幂等重放返回首次 batch/movement/balance，不重复增加库存。
- 数据库唯一约束兜底 receiptLine→batch/movement 一次性。
- 库存流水追加写且不可覆盖；采购状态不能代替库存数量。
- 媒体附件可选，不参加入库数据库事务。

## 契约影响

- API：新增采购策略、采购单、审批、到货、库存查询和附件 API。
- 数据库：后续建议新增 V13 additive 表/索引；本 PR 不创建迁移。
- 权限：新增申请、审批、下单、到货确认、策略和附件 ACL；项目角色只扩展可见性。
- 媒体：additive 扩展 PROCUREMENT_ORDER/PROCUREMENT_RECEIPT ownerType 和四类 purpose，不改变 mediaId 或存储边界。
- UI：采购列表、创建/编辑、详情、审批、分批到货、到货详情和策略设置。
- MQTT、知识、RAG、Agent：无影响。

V13 数据保留与回滚：不得修改 V1-V12；必须验证 V1→V13 和含既有 V12 事实的 V12→V13。应用回滚时保留新增表，不执行破坏性 down migration；真实验证只使用隔离数据库或明确备份，并核对 component/spec/media/PM-001 事实前后不变。

## 评审方法

1. 产品负责人逐项确认 D1-D10。
2. 后端评审 V13、锁序、事务、金额分摊、唯一约束、幂等重放和故障点可实现性。
3. 前端评审路由、字段顺序、金额/数量/进度、附件 ACL、状态和三视口可实现性。
4. 三方意见写回同一契约，不另建私有字段表。
5. 全部确认后产品修订 v1.0、勾选清单并标记 FROZEN，再合入 dev。
