# Week 6 Product Spec / 第六周产品冻结文档

USN Lab Hub IoT · 一个半月 MVP 收尾周

主题：测试、文档、答辩准备

## 1. 本周定位与目标

第六周是一个半月 MVP 的收尾周，只做巩固、验证和呈现，不新增业务功能。

本周目标：

1. 冻结一个半月 MVP 功能范围。
2. 输出最终验收清单，覆盖 telemetry 到公开展示的完整链路。
3. 输出 10 分钟以内的正式演示脚本。
4. 明确演示启动顺序和故障预案。
5. 整理老师审阅要点、PPT 内容大纲、录屏镜头清单。
6. 定义产品、前端、后端三方验收产物。
7. 提出第七周候选方向，但不在本周实现。

## 2. 一个半月 MVP 冻结范围

### 2.1 纳入冻结的功能

```text
MQTT telemetry 上报
MySQL 数据落库（原始 payload + voltage/current/power）
latest 接口与前端实时卡片
history 接口与功率历史曲线
告警规则：power > 100W → WARNING，支持去重
规则建议：告警关联建议，PENDING / CONFIRMED / IGNORED
指令下发：SET_SAMPLE_INTERVAL，intervalSeconds = 5
MQTT ACK：command / ack Topic，10 秒超时
操作日志：HANDLE_ALERT / CONFIRM_RECOMMENDATION / SEND_COMMAND / RECEIVE_ACK
健康评分：100 - 离线40 - OPEN告警30
公开展示页：/iot/public，只读，只展示 power-monitor / PM-001
登录后总览页：/iot/overview 摘要区
```

### 2.2 不纳入的功能（第七周及以后）

```text
SSE / WebSocket 实时推送
第二台设备接入
Agent 自动控制
可配置规则引擎
消息队列或时序数据库
完整项目/设备 CRUD
复杂权限矩阵
PPT 最终视觉以外的自动化工具
```

## 3. 当前完整业务闭环

```text
PM-001 上报 telemetry
    │
    ▼
后端解析并写入 MySQL
    │
    ├──→ latest 接口 → /iot/pm001 实时卡片
    │
    ├──→ history 接口 → /iot/pm001 功率历史曲线
    │
    ├──→ 告警规则 (power > 100W) → OPEN WARNING
    │
    ├──→ 规则建议 → /iot/pm001 建议卡片
    │
    ├──→ 健康评分 → /iot/public 与 /iot/overview
    │
    └──→ 公开聚合接口 → /iot/public 访客页
    │
管理员确认建议 → 下发 SET_SAMPLE_INTERVAL
    │
    └──→ MQTT command → 模拟器/硬件
                │
                └──→ MQTT ack → 指令状态 ACKED
                            │
                            └──→ 操作日志
```

读链路面向访客和管理员公开，控制链路仅对登录管理员开放。

## 5. 演示启动顺序

演示或答辩前必须按以下顺序启动：

| 顺序 | 组件 | 检查点 | 预期耗时 |
|---|---|---|---|
| 1 | MQTT Broker | `localhost:1883` 可连接 | 10 秒 |
| 2 | MySQL | 数据库可达，Flyway 迁移完成 | 20 秒 |
| 3 | 后端 | `http://localhost:8080` 健康检查返回 200 | 30 秒 |
| 4 | PM-001 模拟器/硬件 | 每 5 秒上报 telemetry | 10 秒 |
| 5 | 前端 | `http://localhost:5173` 可访问 | 15 秒 |

验证脚本：

```bash
# 1. 检查 Broker
mosquitto_sub -h localhost -p 1883 -t 'iot/power-monitor/PM-001/telemetry' -v

# 2. 检查后端健康（若存在健康端点）
curl http://localhost:8080/actuator/health

# 3. 检查公开接口
curl http://localhost:8080/api/iot/public/projects/power-monitor

# 4. 检查前端
curl http://localhost:5173
```

## 6. 老师审阅要点

1. **闭环完整性**：从 MQTT 上报到告警、建议、指令、ACK、日志是否可端到端复现。
2. **数据可追溯**：MySQL 中能否查到原始 payload 和指标数据。
3. **健康评分可解释**：给定设备状态和告警数量，能否手动复算 score 和 level。
4. **公开页安全性**：公开接口是否未返回用户隐私、控制入口、MQTT 凭证。
5. **演示可行性**：10 分钟脚本是否能在模拟器独立支撑下完成。
6. **代码与文档一致性**：`04_API_CONTRACT.md`、`05_MQTT_CONTRACT.md` 与实际接口是否一致。
7. **风险意识**：是否准备了硬件离线、接口报错等故障预案。

## 9. 第七周候选方向

第七周及以后只做路线建议，不在第六周实现。候选方向按优先级排列：

1. **WebSocket / SSE 实时推送**
   - 当前页面靠轮询刷新，实时性不足。
   - 建议后续引入 SSE，把 MQTT 数据变化主动推送到前端。

2. **第二台设备接入**
   - 验证多项目、多设备扩展能力。
   - 建议接入温湿度传感器或学生作品，复用现有 Topic 规范。

3. **规则引擎可配置化**
   - 当前告警阈值 hardcode 为 100W。
   - 建议后续支持管理员配置阈值、持续时间和告警等级。

4. **Agent 运维助手（只读建议）**
   - 读取设备数据、历史趋势、告警和日志，生成自然语言建议。
   - 高风险控制仍保留人工确认。

5. **时序数据库评估**
   - 当数据频率提高后，评估 InfluxDB / TimescaleDB 替代 MySQL 存储指标。

6. **移动端适配与公开门户**
   - 优化公开页在手机上的展示，建设实验室成果门户。

## 10. 契约一致性声明

第六周不修改 `04_API_CONTRACT.md` 和 `05_MQTT_CONTRACT.md` 中已冻结的字段。本周新增的四份文档仅用于验收、演示和风险预案，不产生新的 API 或 MQTT 消息。

若在三方验收过程中发现契约与实际实现不一致，按以下流程处理：

1. 记录差异：字段名、影响范围、发生场景。
2. 评估影响：是否阻塞演示、是否影响安全、是否破坏前后端联调。
3. 决策：差异较小且不影响已冻结字段，可在对应开发分支修复；差异较大需产品确认后再修改契约文档。
