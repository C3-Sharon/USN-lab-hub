## 1. 项目定位

USN Lab Hub IoT 是在现有成员管理系统基础上建设的实验室硬件项目管理与智能运维平台。平台以项目和设备资产为核心，通过 MQTT 接入真实硬件数据，把分散的硬件成果沉淀为可管理、可监控、可演示的数字资产。

一句话目标：在一个半月内完成真实硬件 MQTT 联动和完整业务闭环，并为后续设备规模化接入、规则引擎、实时推送、时序数据和 Agent 运维助手预留演进路径。

## 4. 当前完整业务闭环

```text
PM-001 上报 telemetry
    │
    ▼
后端解析并写入 MySQL
    │
    ├──→ latest 接口 → 前端实时卡片
    │
    ├──→ history 接口 → 功率历史曲线
    │
    ├──→ 告警规则判断 (power > 100W) → OPEN WARNING
    │
    ├──→ 建议生成 (缩短采样间隔)
    │
    ├──→ 健康评分计算 (100 - 离线扣分 - 告警扣分)
    │
    └──→ 公开聚合接口 → /iot/public 访客页
    │
管理员确认建议 → 下发 SET_SAMPLE_INTERVAL
    │
    └──→ MQTT command → 模拟器/硬件
                │
                └──→ MQTT ack → 指令状态 ACKED
                            │
                            └──→ 操作日志 SEND_COMMAND / RECEIVE_ACK
```

闭环中的读链路和健康评分对访客公开，控制链路仅对登录管理员开放。

## 5. 真实硬件与模拟器方案

当前演示使用 `scripts/pm001_simulator.py` 作为稳定数据源。模拟器严格复用与真实硬件相同的 MQTT Topic 和 JSON 协议：

- Topic：`iot/power-monitor/PM-001/telemetry`
- Payload 包含 `projectCode`、`deviceCode`、`reportTime`、`metrics{voltage,current,power}`、`status`
- Command Topic：`iot/power-monitor/PM-001/command`
- Ack Topic：`iot/power-monitor/PM-001/ack`

真实硬件接入路径：

1. 在硬件固件中按上述 Topic 和 JSON 格式上报 telemetry。
2. 订阅 command Topic，解析 `SET_SAMPLE_INTERVAL` 并更新采样间隔。
3. 执行后通过 ack Topic 返回 `commandId` 和 `status=ACKED`。

由于真实硬件在现场网络、电源和固件稳定性上存在不确定性，演示和日常调试均保留模拟器作为兜底。

## 6. 当前风险

| 风险 | 影响 | 当前应对 |
|---|---|---|
| 真实硬件不稳定或不在现场 | 演示中断 | 使用 `pm001_simulator.py` 兜底，协议与真实硬件一致 |
| 健康评分规则过于简单 | 老师质疑智能化程度 | 明确这是 MVP 最小可解释口径，长期会扩展为加权模型 |
| 公开接口暴露过多信息 | 隐私或安全风险 | 已定义白名单/黑名单，接口只返回只读摘要 |
| 演示时间不足 | 无法完整展示闭环 | 演示脚本控制在 10 分钟以内，提前预演 |
| 第六周文档和 PPT 工作量集中 | 答辩准备仓促 | 第五周已输出老师审阅版说明，第六周专注排版和录屏 |

## 8. 一个半月后的长期路线

1. **扩展硬件资产库**：接入更多开发板、检测模块、学生作品和客户项目。
2. **增强实时能力**：引入 WebSocket 或 SSE，把 MQTT 数据变化主动推送到前端。
3. **增强规则能力**：完善规则引擎、设备健康评分、趋势分析和告警处理流程。
4. **增强数据底座**：数据频率提高后引入消息队列，并评估 InfluxDB / TimescaleDB 等时序数据库。
5. **增强展示能力**：建设项目大屏、设备拓扑、公开成果门户和移动端适配。
6. **建设 Agent 运维助手**：读取设备数据、历史趋势、告警和日志，生成可解释建议；高风险控制保留人工确认。
7. **沉淀为实验室基础平台**：作为硬件项目立项、接入、展示、维护、复盘的统一入口。
